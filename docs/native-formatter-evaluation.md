# Native CSS and JavaScript formatter evaluation

Decision update (2026-10-22): user deferred embedded CSS/JavaScript formatting. The following recommendation is retained as research only; no dependency or integration is selected.

Reviewed 2026-10-22. This is a research recommendation only; no dependency, helper, or package change is approved by it.

## Decision

Use the standalone **Oxfmt native CLI** as the first implementation candidate if a bundled Rust helper process is acceptable. Current Oxfmt language-support documentation classifies JavaScript/JSX, TypeScript/TSX, CSS/SCSS/Less and related formats as native Rust formatting. Its standalone release binary runs without Node.js, while HTML and other Prettier-backed formats are skipped. Formatting only the CSS and JavaScript source ranges already extracted by Postie's markup scanner avoids the HTML fallback entirely. The official v0.73.0 release, published 2026-10-13, contains CSS formatter documentation changes; the release index also lists v0.74.0, so v0.73.0 is the reviewed pin here, not a claim that it is latest. Oxc is MIT-licensed; review the selected release's bundled third-party notices before distribution. [Oxfmt language support](https://oxc.rs/docs/guide/usage/formatter/language-support) · [Oxfmt standalone CLI](https://oxc.rs/docs/guide/usage/formatter/quickstart) · [Oxfmt v0.73.0 release](https://github.com/oxc-project/oxc/releases/tag/oxfmt_v0.73.0) · [Oxfmt releases](https://github.com/oxc-project/oxc/releases) · [Oxc license](https://github.com/oxc-project/oxc/blob/main/LICENSE)

This is a **compiled Rust executable**, not a Swift formatter framework or in-process Swift API. The simplest bridge is Swift `Process`: send one bounded extracted block to stdin with `--stdin-filepath block.js` or `block.css`, collect stdout, then terminate the child on cancellation. On nonzero exit, timeout, or output-limit failure, keep that block's original source. This follows Postie's display-only and byte-preservation contract; transmitted, captured, and exported bodies remain unchanged. [Oxfmt stdin usage](https://oxc.rs/docs/guide/usage/formatter/quickstart) · [Postie body-format plan](body-format-plan.md)

Keep the integration isolated from project state: invoke the standalone binary directly (no shell or npm package), pass a fixed app-owned JSON config with `--config`, use a controlled empty working directory, and do not enable plugins or sorting. Oxfmt documents that explicit config disables nested config lookup, but also reads `.editorconfig` and defaults to `.gitignore`/`.prettierignore` from the current directory when no ignore path is given. Therefore the controlled working directory and explicit ignore policy are part of the proposed design, not optional cleanup. Do not pass whole HTML to Oxfmt: its HTML path is Prettier-backed in the npm distribution and skipped by the standalone binary. [Oxfmt CLI options](https://oxc.rs/docs/guide/usage/formatter/cli) · [Oxfmt configuration lookup](https://oxc.rs/docs/guide/usage/formatter/config) · [Oxfmt language support](https://oxc.rs/docs/guide/usage/formatter/language-support)

The public interface documented for the standalone formatter is CLI-oriented; the documented Node API would violate the no-JavaScript-runtime requirement. No current release binary sizes, per-call latency, peak memory, or app install-size delta were established in this review. Bundle, signing, cancellation, configuration isolation, parser-error behavior, and supported macOS architectures need a focused packaging and synthetic-input check before any dependency decision. Runtime and resource performance remain unmeasured. [Oxfmt quickstart](https://oxc.rs/docs/guide/usage/formatter/quickstart) · [Oxfmt v0.73.0 release](https://github.com/oxc-project/oxc/releases/tag/oxfmt_v0.73.0)

## One alternative: narrow native Rust helper

If avoiding a general-purpose formatter CLI becomes more important than minimizing build work, evaluate a small Rust helper that links the published [Malva](https://docs.rs/malva/latest/malva/) CSS formatter and [dprint TypeScript plugin](https://docs.rs/dprint-plugin-typescript/latest/dprint_plugin_typescript/) Rust formatting API. Malva exposes `format_text` for CSS-family input and returns errors for syntax errors; the TypeScript plugin crate exposes `format_text` for JavaScript/TypeScript input. Both projects use MIT licensing. Linking these Rust APIs directly does not require dprint's Wasm runtime or the dprint executable. The helper would still be a compiled native process, not Swift-only, and would need a deliberately narrow stdin/stdout protocol, Cargo build configuration, per-architecture packaging/signing, and lifecycle handling in Swift. These crate docs expose Rust APIs, not a Swift package contract; no stable C ABI is established by this evaluation. [Malva API](https://docs.rs/malva/latest/malva/) · [Malva license](https://github.com/g-plane/malva/blob/main/LICENSE) · [dprint TypeScript API](https://docs.rs/dprint-plugin-typescript/latest/dprint_plugin_typescript/) · [dprint plugin architecture](https://dprint.dev/plugins/) · [dprint TypeScript manifest and license](https://github.com/dprint/dprint-plugin-typescript/blob/main/Cargo.toml)

This route avoids shipping dprint's stock Wasm plugins but increases integration and maintenance work: pin the two formatter crates and transitive dependency graph, build and sign a helper for supported macOS architectures, and verify that Wasm features are not enabled. Its final binary size and runtime/resource use are unknown; it is not established to be smaller or faster than Oxfmt. The crates are Rust-native; they are not Swift-native and do not create an in-process Swift API without additional FFI work.

## Other candidates considered

| Candidate | Assessment |
|---|---|
| **Biome CLI** | Credible compiled Rust alternative: its current support table marks JavaScript/TypeScript, CSS and SCSS formatting as supported, and its project states it does not require Node.js. It is a broader formatter/linter CLI; it offers no simpler Swift-facing boundary than Oxfmt for this display-only use. MIT or Apache-2.0. [Language support](https://biomejs.dev/introduction/language-support/) · [Project and license](https://github.com/biomejs/biome) |
| **dprint stock plugins** | Not native-process integration by default: official TypeScript/JavaScript and community Malva plugins are distributed as Wasm plugins. The underlying Rust crates can instead be linked into the narrow helper described above, without embedding dprint itself. [Plugin types and list](https://dprint.dev/plugins/) |
| **Lightning CSS** | Native Rust CSS parser/transformer, but its documented purpose includes syntax lowering, bundling and CSS minification/optimization. It supplies no JavaScript formatter and is not a source-preserving CSS pretty-printer equivalent for this use. [Rust API](https://lightningcss.dev/docs.html) · [Minification behavior](https://lightningcss.dev/minification.html) |
| **clang-format / LibFormat** | Clang exposes a JavaScript language kind, but its formatter is C++ LibFormat and does not cover CSS. It is not a two-language parser/printer fit for this feature. [LibFormat](https://clang.llvm.org/docs/LibFormat.html) · [Language kinds](https://clang.llvm.org/docs/ClangFormatStyleOptions.html) |
| **Oxc formatter crates alone** | Do not rely on older descriptions of Oxc as JS-only for this decision: current Oxfmt docs include native CSS-family formatting. For this app, the supported standalone Oxfmt CLI is the lower-friction route; a direct Rust library route would still require an app-owned bridge. [Current Oxfmt language support](https://oxc.rs/docs/guide/usage/formatter/language-support) |

## Constraints for any follow-up

- Preserve Postie's current behavior: format only known, extracted embedded CSS/JS blocks; leave unknown or invalid blocks unchanged and keep formatting display-only. Embedded formatting is currently outside the completed slice, and the plan requires approval before adding a dependency. [Body-format plan](body-format-plan.md) · [Historical rejected JavaScript formatter evaluation](embedded-formatter-evaluation.md)
- Use no JavaScript runtime or JavaScript/Wasm fallback. In particular, do not use Oxfmt's Node package or dprint's stock Wasm plugin path.
- Before adoption, test the chosen pinned artifacts on synthetic CSS and JavaScript inputs, malformed input, configured JSX/module syntax, cancellation, output bounds, and an isolated working directory. No such prototype or benchmark was run for this evaluation.
- Recheck the current release, license notices, macOS architecture support, and exact packaged binary size at approval time. No current Oxfmt or custom-helper bundle-size estimate is asserted here.
